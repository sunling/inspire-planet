# 会议转写：手动下载与归档

转写下载只在手动运行 GitHub Actions 时执行，已移除全部定时触发。下载成功后直接提交到公开仓库的 `main`，不创建 PR；运行前须确认该场转写可公开。

## 1. 手动下载最新会议

1. 打开 [Transcript download](https://github.com/sunling/inspire-planet/actions/workflows/meeting-content.yml)。
2. 点击 **Run workflow**，选择 `main` 并运行，无需填写参数。
3. 查看运行日志和 `main` 提交记录。最新会议已归档时正常跳过，不回退下载更早场次。

工作流需要有效的 `TENCENT_MEETING_TOKEN` Secret、`contents: write` 和 `pull-requests: read` 权限。原先的 `CONTENT_AUTOMATION_ENABLED` 变量不再使用，可以删除。

## 2. 下载结果与失败处理

期次可确认时写入 `events/`；期次不明时写入公开的 `incoming/meetings/`，待人工确认。不会生成文章、纪要或金句。

录制列表完整分页且同时匹配 `meeting_id` 和 `sub_meeting_id`，确认该场录制存在。优先读取该场会议元数据中明确标为“转写”的文件；文字转写 ID 可以与原生音视频 ID 不同，不要求两份列表相等。没有明确转写候选时才尝试该场原生文件。候选与其他场次归属冲突时停止；同一场内忽略空转写，选择完整正文最长的一份，并列且内容不同、文件重复、分页不完整或超出上限时停止。

针对误入会议产生的独立短记录，另增加**跨场次筛选**：按选定的本地日期收集候选（最新下载默认北京时间），最多 8 场；在授权读取阶段统计真正发言正文中的汉字、字母和数字，不计发言人、时间戳、空白和标点。当前门槛为 **1000 个有效字符**，可在 `scripts/meeting-project.json` 调整。同一天只有一场达标才选择；多场均达标时不能直接取最长，需人工核对。读取失败不会当作空转写。读取同一转写分页遇到上游 HTTP 500／502／503／504 时，分别等待 2 秒、4 秒，最多尝试 3 次；持续失败通常停止，不把 HTTP 错误当作空转写。仅当第一页持续 HTTP 500、且另一个已验证 schema 的只读段落索引接口明确返回 `total=0`、`pids=[]`、`audio_detect=1` 并无后续分页时，才能认定该文件无段落并继续检查同场下一份；索引非空、缺字段、工具不可用或再次失败均保留原失败。分页中途失败一律停止，不使用不完整正文。日志只显示开始时间、有效字符数和是否达标，不输出正文／姓名。

字数只用于排除近乎空的记录，不用于给 EP 编号。最新日期全是短记录时停止，不自动跨天取另一份最长稿；可改为按实际会议日期补录。真实会议若确实少于门槛，也需先人工核对，不能为了通过而拼接或补造正文。

转写未生成时稍后手动重试；凭据失效、权限不足或实例不明确时由维护者核对，不猜期数、不跨期取文件。

### 已归档会议也能做只读实测

打开 [Content CI](https://github.com/sunling/inspire-planet/actions/workflows/content-ci.yml)，点 **Run workflow**，在 `check_date` 填北京时间会议日期（EP42 为 `2026-10-24`）。测试 PR71 尚未合入时，在 **Use workflow from** 选择 `fix/transcript-content-selection`，合入后选择 `main`。不要在功能分支运行 `Transcript download`：它会写入公开 main，因此只允许默认分支运行，功能分支的整个 job 会显示 skipped，这不代表筛选代码运行失败。

`ep40-readonly` 是沿用的内部 job ID，实际读取日期以 `check_date` 为准。该步骤强制重新读取远程完整转写，不因已归档而跳过；随后与该日期唯一归档比较发言人、时间及忽略空白后的正文，日志仅显示段落数量与是否一致。内容不同会提示另行核对，不覆盖归档；本地归档若不是标准原始转写格式，只跳过逐段比对并明确说明，远程格式／读取失败仍使测试失败。全文只存 runner 临时缓存并始终清理；没有发布步骤，权限仅为读取。

完整读取失败后，Content CI 自动执行只读诊断：只检查所选日期内已验证归属的文件，每文件用 `pid=0, limit=1` 单次请求，遇到 HTTP 500 时再用已验证的段落索引接口核验，全部请求合计最多 16 次探测。日志只显示候选来源（转写元数据／原生录制列表／两者共有）、时间、数量与 HTTP 状态，不输出正文、文件 ID 或响应。它用于区分大分页请求失败与文件特定失败；小请求成功不等于整份可读，也不会跳过失败候选、替代完整验证或使任务变绿。若仍需报腾讯支持，提供失败工具、运行时间、状态和这些脱敏结果即可。

## 3. 历史会议转写：查找或按日期补录

打开 [历史会议转写 · 查找与补录](https://github.com/sunling/inspire-planet/actions/workflows/meeting-history.yml)，点 **Run workflow**，在 **Use workflow from** 选择 `main`。

- **查找未归档会议**：操作选择 `查找未归档会议`（默认），日期留空，运行后在日志查看未归档会议的真实日期。此操作只扫描，不下载全文、不写入 main。
- **按日期补录**：操作选择 `按日期补录`，填写会议日期 `YYYY-MM-DD`（例如 `2026-09-26`），再选择**该日期所属的时区**：默认 `Asia/Shanghai`（北京时间），也可选择 `America/Los_Angeles`（美西时间）或 `UTC`。运行后只在该日候选中恰好一场达到有效对话门槛时，尝试将选中转写直接提交到 `main`。
- **提交后检查**：检查 `main` 上新增的转写、日期、来源、期次和公开范围；该工作流不创建 PR。

会议日期严格按**你选定的时区**解释，不会同时用多个时区猜测。同一当地日期有多场时，在读取阶段按上述有效字数筛选；多份达标、没有匹配、读取不完整或仍有歧义时停止。准备和只读扫描仍只看元数据，不提前下载正文。

历史录制可能受 API 可用期限与旧录制归属限制；如失败请交由维护者核对。

## 4. 什么时候需要维护者？

如果手动运行持续无法下载、没有权限写入 main、匹配到错误会议或期次不明，请维护者检查仓库设置、凭据和工作流日志。**不要在 Issue、PR 或日志里粘贴 Token 或私人逐字稿。**

详细的会议实例匹配、去重、时间范围、授权门禁、旧记录边界、测试命令等见 [转写自动化技术维护说明](../scripts/meeting-content-technical.md)。

完成转写归档后，下一步是 [内容生成与审核](content-workflow.md)。

## 5. 音视频下载与保留一天

当前脚本只下载转写，没有下载音视频，也没有上传媒体 artifact。腾讯会议的 `get_record_addresses` 支持获取录制下载地址，实际可用性取决于该场录制是否就绪和账号下载权限，需要单独接入并验证。

若以后经授权通过 Actions 暂存媒体，可用 `actions/upload-artifact` 的 `retention-days: 1` 设置一天保留期；这不限制下载时的峰值空间，也不删除用户已下载到本地的副本。媒体不提交 Git。公开仓库的 artifact 可被有仓库读取权限的登录用户下载，因此不能用一天保留期代替原声与肖像公开授权；私人录制优先直接下载到本地被忽略的 `replays/`。

大小应以实际文件或响应大小为准。仅作码率估算：两小时 64–128 kbps 音频约 58–115 MB；0.5–2 Mbps 视频约 450 MB–1.8 GB（十进制，不含额外开销）。一天保留不能避免当天占用超额。

参考：[腾讯会议 MCP 工具](https://meeting.tencent.com/support/topic/2233/index.html)、[artifact 保留期](https://github.com/actions/upload-artifact#retention-period)、[GitHub 存储额度](https://docs.github.com/en/billing/reference/product-usage-included)。
