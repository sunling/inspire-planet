# 会议转写自动化：技术与维护参考

> 本文供维护者排错和验证使用。日常下载、人工审核与历史补录入口请先看 [会议转写操作指南](../docs/meeting-content.md)。

## 日常：不填日期、EP 或过滤器

- Actions → **Transcript download** → Run workflow → 选择 `main`。日常入口没有输入框；API 也不需要 EP。
- 一次配置在 [meeting-project.json](../scripts/meeting-project.json)：精确标题 `启发星球，互相赋能`、90 天回看、已核对锚点 `2026-10-10 / EP40 / 13319006708380765410`。会议周期 ID 可变化，发现按精确标题，不锁死旧 ID。
- 首次只需已授权的 `TENCENT_MEETING_TOKEN` Secret；不需要模型、API Key 或外部内容服务。Token 不放变量、参数、聊天或日志。
- 新转写会在通过内容检查后直接提交到 `main`；Actions job 需要 `contents: write` 与只读的 `pull-requests: read`（用于去重），不依赖创建 PR 的权限或仓库设置。提交即公开，因此在运行前需确保该场转写已获准公开。
- 生产入口始终使用默认分支代码，只有已合并的更改才会影响定时任务；工作流仅从默认分支运行。

## 发现、去重与期次

- 查询真实 UTC 时间区间 `[now−90 天, now]`，完整翻页（最多 200 页），再次排除窗口外／未来实例；仅精确匹配项目标题，按实际开始时间取最新，不取账号任意最新一场。
- 先读取远端 `main` 与**全部开放 PR**的固定 head SHA；按既有转写日期和持久实例信息去重。实例键为 `sha256(meeting_id, sub_meeting_id, UTC start_time)`，不是共享周期 ID。
- 最新场已入库／已有草稿时 clean skip，不回退抓更旧会议，不覆盖或重复读取正文。主分支中的文件与持久实例信息去重；不再创建内容分支或 Draft PR。
- 优先使用已核对日期映射（初始为 EP40）。只有完整列表包含唯一锚点、同年同周期、其后仅一场且恰好是连续下一次时，才递增为 EP41；7 天间隔仅为连续性保守门禁，不按周数推 EP，不看历史最大 EP。
- 漏期、多场、回补、跨年、周期切换或锚点不可见时不猜 EP，也不阻塞下载。后续超出已核对的一次递增范围先待确认，审核后更新配置锚点，不要求每次运行填写字段。

## 两种公开归档

- EP 可证明：`events/{year}/{YYYYMMDD}-epXX/transcript.txt`、`metadata.json` 与总索引。
- EP 不明：`incoming/meetings/{sha256-instance-key}/transcript.txt`、`metadata.json` 与待确认 `README.md`；不改活动索引，不生成网站 JSON。
- **两条路线都会直接提交到公开 `main`**，提交后任何人都可见，不经过 PR 审核。metadata 保留实例、UTC 日期与录制文件身份；确认期次时保留它，避免重抓。
- 提交仅允许本次固定路径；检查默认分支、HEAD、工作区、暂存区、远端同名分支。无 force push；推送前确认远端 `main` 仍与计划基线一致，只提交白名单内文件，推送后读回 SHA。
- 不调用模型，不生成文章、纪要、卡片或图片；不创建 PR、不发消息、不修改网站或社交平台。网站只读取审核后 `main` 的既有 JSON，本流水线不生成它们。

## 高级历史补录／检查

- 网页入口为 **历史会议转写 · 查找与补录**：选择 `查找未归档会议`（只读扫描）或 `按日期补录`（按 `date` + `timezone` 精确匹配），默认时区 `Asia/Shanghai`。`pick`、`fetch-check`、`connectivity` 仅保留在维护者 CLI，不出现在普通网页表单；网页输入不接受 EP。
- **期数不是选择依据**。腾讯会议没有期次概念，只有每场会议的实例（meeting_id / sub_meeting_id / 开始时间）；`ep{N}` 只是本仓库 `events/{year}/{YYYYMMDD}-epXX/` 的命名约定，**期数每年重置**（2025 为 ep02…ep50，2026 又从 ep01 开始），且若干目录日期是**迁移遗留**（如 13 个目录共用 `20250428`，`20260808` 被 ep31/ep32 共用，并且缺 ep11/ep29），早 2025 期次甚至可能属于其他会议标题。因此**目录日期不可信**，本流水线**从不按期数或目录推算抓取日期**；抓取目标日期只来自真实腾讯会议数据。
- 仓库目录映射最多作为**只读扫描中的展示提示** `ep_hint`，且仅在该日期唯一对应一个期次目录时显示；它**不参与选择，也不能用于抓取**。
- `date` 采用明确选定的 `--timezone`（默认北京时间；还可用 UTC、美西），只按该时区当天开始时间判断，必须**唯一命中一场**项目会议；同日多场、无命中或超出回看窗口则停止，不任选一场。
- 用**只读扫描编号**选择：先空输入运行扫描得到编号行，再以 `pick=N`（工作流 `pick` 字段）抓取第 N 场。编号按真实日期升序、只统计**未归档**场次；`pick` 与 `date` 二选一（仅维护者 CLI）。重新运行会基于同一回看窗口与归档状态重算编号；序号越界、格式无效或用于非 `prepare` 命令都会停止。
- 选中场次后，`publish` 复用日常实例身份、主分支／开放 PR 去重、白名单写入与直接提交链路。期次目录的映射仍来自 `main`／开放 PR 中**现有同 UTC 日期的 event 目录**（即使目录尚无转写）；无映射或冲突则进入公开 `incoming/meetings/{实例哈希}/` 待确认。历史不调用下一期推断，既有目录的旧日期口径不自动迁移。
- **留空 = 只读扫描**：无 date 也无 pick 时，工具在最近 **12 个月**内按 **≤90 天窗口**分块调用 list-ended，排除未来／窗口外场次与重复实例，最多探测 **20** 场**未归档**的项目会议。每场只调用**元数据** `get_records_list` 判断能否读取，**不拉取正文、不写任何公开文件**。输出只有计数、**编号、真实日期与星期**、可选 `ep_hint`、可读布尔与静态原因（不打印原始 payload、Token、姓名或其他会议）。扫描始终退出 0，即使仍有未归档场次。
- 只读扫描的“可读”判断：优先看该场 list-ended 记录里是否有 `转写` 类型录制文件；没有时再用限定到该场（meeting_id + sub_meeting_id）的原生录制列表兜底区分“仅录制未转写”与“无录制”。该会话 `records[]` 计数已知不可靠（可能为 0 而实际已有转写），因此扫描结果是保守下限，不保证已经能读全。
- `fetch-check` 不查询 GitHub，也不使用期数或目录日期；即使本地已有稿仍强制读远程全文，仅缓存 `.git/meeting-content-fetch-check.txt`，公开文件不变；运行结束清理 runner 缓存。已有转写／实例时跳过，不覆盖。
- 维护命令（Actions 注入 Secret）：`python3 scripts/latest_transcript.py fetch-check --date 2025-12-14 --timezone Asia/Shanghai`、`scan`、`prepare --pick 3` / `prepare --date 2025-12-14`，其后使用同一 `fetch / write / publish`。日常入口仍然零输入。
- **已知历史限制（本轮不变）**：历史周期会议 guard 保持严格——会议／子会议限定后，原生录制集合必须与本次文件集合**完全一致**，不放宽为包含关系，也不跨日期选择最长录制。2025 年旧协议的录制归属问题会使这些历史场次在 `fetch` 阶段失败即停止，本流水线不会绕过该保护；需要人工先核对录制归属。
- MCP 源适配合同不变：三个只读工具、运行时 schema、完整模式 `is_compact=false`、已观察的 HTTP/JSON 包装、列表完成标志、完整段落分页及上限。未知结构／分页缺失均安全停止，原始错误隐藏。

### 同一场会议存在多个转写文件

- 无论会议列表的 `records` 为空，还是列出了多个录制文件，都只在**同一个 meeting_id + sub_meeting_id** 的完整录制集合内读取转写候选，并逐一完成分页校验；忽略空转写，选**实际发言正文字符数最多**的一份。这里的「最长」不是文件名、录制时长或包含说话人／时间戳的格式字符数。
- 录制集合超过 8 个、出现重复或跨子会议文件、分页不完整时安全停止；正文最长长度并列且内容不同，也停止并人工核对。
- 结果仅输出候选数量和文字长度，不输出转写正文或文件 ID。最长不等于必然完整；该转写将直接出现在公开 `main`，运行前必须确认可公开。

## 安全与排程

- Tencent Secret 只注入发现／读取步骤；GitHub Token 只用于归档去重及提交。无原始 payload、转写日志或 artifacts；缓存留在 runner `.git`，任务结束清理。
- 生产 `main` 门禁不变：排程只在默认分支运行，且需 `CONTENT_AUTOMATION_ENABLED == true`（手工 dispatch 不受该变量限制）。
- **排程窗口（按会议实际结束时间设定）**：启发星球会议为北京时间周六 08:00–10:00，即 UTC 周六 00:00–02:00，时长不超过 2 小时。因此排程为 **UTC 周六 02:07 / 02:17 / 02:27 / 03:07 各一次**（`7,17,27 2 * * 6` + `7 3 * * 6`，北京时间 10:07 / 10:17 / 10:27 / 11:07），每周最多 4 次尝试，用于覆盖转写生成延迟。11:07 为会议延长和转写生成延迟留出兜底；仍未就绪则本周自动尝试结束，可手工 dispatch 补跑。**仅 schedule 运行**按北京时间周六当天开始的已结束会议筛选，不会在本周会议仍在进行时回退抓上周未归档的会议；手工运行和历史补录保持原有检索范围。已归档时安全跳过，不重复拉取、不重复提交。
- 排程也遵循 GitHub 的限制：定时触发可能延迟（因此 10 分钟的间隔在极端情况下可能挤在一起，但每次运行都是幂等的），且仓库长期无活动时定时任务会被自动停用；需要时可手工 dispatch 补跑。
- Actions 的 `contents: write`、`pull-requests: read` 权限与腾讯 Secret 是工作流运行所需条件；只读成功不证明写入权限可用。

## 验证

- 无密钥：`python3 -m unittest discover -s scripts -p 'test_meeting_content.py' -v`、`python3 -m unittest discover -s scripts -p 'test_latest_transcript.py' -v`、`python3 scripts/check-content.py`；可用时运行 actionlint。
- 已注册 `Content CI` 的 push／PR 仅跑无密钥测试。只有人工 dispatch 才给只读 job Secret，checkout **精确 dispatched `github.sha`**；feature 验证用 `gh workflow run content-ci.yml --ref feat/latest-transcript`，不绕过生产门禁。
- `latest-readonly` 执行零输入真实发现与主分支／开放 PR 去重，验证公开工作区不变，不下载正文、不提交。`ep40-readonly` 保留真实固定本地日期全文检查与缓存清理。`history-scan-readonly` 执行真实 `scan`，验证有界只读扫描（编号、日期、星期、可读布尔）与公开工作区不变。
- 先前 EP40 全文实际成功：Actions run `38785641587`，181 段；本次新增真实运行以 PR 检查和手动 run 为准。
- 合成测试覆盖无新会议／主分支及开放草稿去重、下一期证明、间隔／跨年待确认、完整下载一次及真实本地 Git/bare 推送；历史本地日期三时区唯一匹配、同日多场失败、`pick` 编号选择与越界失败、有界扫描窗口/探测上限与去重、`ep_hint` 仅唯一目录显示均有合成覆盖。合成 GitHub 响应不冒充真实会议内容。
- 若真实最新仍是已入库 EP40，正确验收结果是 skip；不能据此声称新场次的直接提交已真实跑通。新场次会在下载验证后直接提交到 `main`，无需创建 PR。
